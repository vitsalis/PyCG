# Q8. `raise C` of a package class whose first `__init__` is outside

Adopted by the lead in place of a referee, maintainer's instruction of
2026-11-28. Read at `c7fc8fb3`. Paths are relative to
`evaluation/macro-benchmark/`; a package's files are cited from its root
under `projects/<name>/`, its ground truth is under `ground-truth/`, and
`benchmark-rules.md:<n>` is a line of `evaluation/benchmark-rules.md` at
that commit.

**1. The question.** For `raise C` without a call, where `C` is a package
class whose first `__init__` in the MRO is outside the package, the
micro-benchmark gives an edge to that `__init__`
(`<builtin>.Exception.__init__`) and the macro-benchmark gives none. The
study counted 22 edges; which convention holds?

A scan of every `raise` site of the 60 projects with `sites.py` (a
`raise` site whose name is a package class, following package bases)
finds 16 such sites in 5 packages; the macro graphs have none of the
micro-style edges:

That is 14 caller-callee pairs that the macro graphs lack (marshmallow 1,
structlog 3, vulture 1, tablib 8, flit-core 1; `LoadedConfig.add_scripts`
has no edges in `flit-core.json`, and `flit-core.ledger:17` names the
site). Eight of them are traced and rejected,
each with the reason "an implicit site ... has only package callees"
(`marshmallow.rejected.json`, `structlog.rejected.json` 3,
`vulture.rejected.json`, `tablib.rejected.json` 3; the trace names the
callee `<builtin>.BaseException.__init__`).

The micro cases that rest on the micro rule are `exceptions/custom_str`
(`main -> <builtin>.Exception.__init__` for `raise ParseError`) and
`exceptions/handler_calls_exception_method` (`main.query ->
<builtin>.Exception.__init__` for `raise DbError`).

**2. The ruling.** **Apply "Implicit calls": a `raise` of a package class
without a call adds no edge in the macro-benchmark when the first
`__init__` of its MRO is outside the package; the micro-benchmark keeps
its edge. The difference is stated in both places and is intended.** No
ground truth contradicts it.

Effect: no edge added, removed or renamed; no text changes.

The two alternatives, for a single convention:

| Alternative | Effect |
|---|---|
| Macro follows micro | +14 outside edges (marshmallow 1, structlog 3, vulture 1, tablib 8, flit-core 1); 8 rejected trace edges leave the `.rejected.json` files; the ledger and `check.py` must admit outside callees at `raise` sites, the one exception to "an implicit site has only package callees"; the "Implicit calls" paragraph loses its first case |
| Micro follows macro | `<builtin>.Exception.__init__` leaves `exceptions/custom_str` and `exceptions/handler_calls_exception_method`; the validator observes the call, so it must learn to ignore it; the micro "Instantiation of a snippet class" rule changes for `raise` |

**3. What the rules say.**

Macro "Ground-truth conventions", Implicit calls: "An implicit site has
only package callees (see "The ledger"). Two cases differ from the
micro-benchmark. A `raise` of a package class without a call adds no edge
when the first `__init__` of its MRO is outside the package: `raise
_FieldInstanceResolutionError` in marshmallow (`fields.py:102`), whose
first `__init__` is that of `TypeError`; the micro-benchmark names that
`__init__` (`<builtin>.TypeError.__init__`)."

Rule A lists "an implicit call of code outside the package" among the
trace edges to reject. The ledger: "An implicit site has only package
callees: implicit calls of code outside the package are not edges", and
`check.py` reports "an outside callee at an implicit site".

Micro conventions, Edges, "Instantiation of a snippet class": "A call
`Cls()` and a `raise Cls` without parentheses both instantiate the class.
... Otherwise the edge names it through the nearest class of the MRO that
is outside the snippet".

The rules decide it, as a deliberate difference: the macro text names
this exact case and its micro counterpart.

**4. The evidence.**

- The macro ground truths agree with the macro rule at all 16 sites; no
  ledger has an outside callee at an implicit `raise` site (`check.py`
  would fail).
- The micro-benchmark is validated by observing the run (`validate.py`):
  its edges are calls that the interpreter makes, and the instantiation
  of the class runs `BaseException.__init__` at the raise. The
  macro-benchmark's implicit sites take only package callees because its
  ledger, its site finder and its trace rejections are built on that
  split (an implicit site has package candidates by name only).
- The macro rule matches the macro treatment of other implicit outside
  calls (a `with` on a library object, a `for` over a library iterator:
  no outside edge), and an explicit `raise C(...)` still gives the outside
  `__init__` in both benchmarks (`custom_init_super`, `inherited_init` in
  the micro-benchmark; flit-core's `ConfigError(...)` in the macro).

**5. Against.** One tool scored on both benchmarks is penalised either
way for these 14 pairs, and in the macro-benchmark `raise C()` gets the
outside `__init__` while `raise C` does not, which a reader of the
results must be told. The existing text tells it; changing either
benchmark costs more (a ledger-format exception, or a validator
exception) than the 14 edges weigh.
