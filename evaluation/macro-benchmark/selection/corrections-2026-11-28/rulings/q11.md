# Q11. path: edges that rest on stdlib internals of one platform and version

Adopted by the lead in place of a referee, maintainer's instruction of
2026-11-28. Read at `c7fc8fb3`. Paths are relative to
`evaluation/macro-benchmark/`; a package's files are cited from its root
under `projects/<name>/`, its ground truth is under `ground-truth/`, and
`benchmark-rules.md:<n>` is a line of `evaluation/benchmark-rules.md` at
that commit.

**1. The question.** About 77 edges of `path` (release with
`requires-python = ">=3.9"`, `pyproject.toml:28`) exist only because the
Windows `ntpath` of particular CPython versions, or PyPy 3.11's, calls
back into the `Path` object (a `str` subclass that overrides `replace`,
`__add__` and `__radd__`). Do they count?

| Mechanism | Runtimes | Ground-truth record |
|---|---|---|
| `normcase` `s.replace('/', '\\')`; `splitdrive`/`splitroot` `p.replace(altsep, sep)`; 3.12 `splitdrive` `root + tail` | Windows, CPython 3.9-3.12 (normcase every version) | `path.md` J3; "Library behaviour on supported platforms" (38 call-backs to `Path.replace` and `Path.__radd__`) |
| UNC path without a third separator: `splitroot`/`splitdrive` returns the object itself, then `split`/`join` concatenate (`Path.__add__`) | Windows, CPython 3.11 and 3.12, PyPy 3.11 | Codex audit rounds 1 and 2 (`path.md:417-525`): `dirname`, `basename`, `splitpath`, `glob`, `iglob`, `makedirs`, `renames`, `replace`, `__rtruediv__`, `Path.__new__` |
| PyPy 3.11 `nt` has no `_path_normpath`, so `ntpath.normpath` is Python | Windows, PyPy 3.11 | "Implementation, version and platform combinations" (5 call-backs: `absolute`, `normpath`, `realpath -> Path.__add__`; `copymode`, `copystat -> Path.replace`) |
| `abspath` falls back to Python code after `_getfullpathname` raises `ValueError` for an embedded null (`Path('a\0')`) | Windows | `path.md` J5 (`absolute`, `ismount -> Path.replace`, `-> Path.__radd__`) |

From the ledger: 76 pairs of `path` go to `Path.replace`, `__add__` or
`__radd__`; 21 are traced; of the other 55, 49 have only Windows,
`ntpath`, UNC or PyPy 3.11 witnesses in their notes (22 `replace`, 17
`__add__`, 10 `__radd__`). The rest of the 77 are the callers' other
Windows edges.

**2. The ruling.** **Apply the two path rulings; no change.** Each edge
needs a witness on one admitted (implementation, version, platform)
combination with that runtime's real library code; how few combinations
produce it does not matter.

Scope: the judgements read one patch release per minor version (CPython
3.9, 3.10.14, 3.11.9, 3.12, 3.13 to 3.15; PyPy 3.10 v7.3.19, 3.11
v7.3.20). The rules do not say whether an edge that only some patch
releases of a minor version make counts, and none of these edges needs
it: the mechanisms above are the same in every 3.9 to 3.12 patch release
(the C `splitroot` and `normpath` arrived in feature releases, 3.13 and
3.11).

Effect: 0 edges; no text of `benchmark-rules.md` changes.

**3. What the rules say.**

- Judgements (`benchmark-rules.md:1957-1959`): "A branch on the platform
  runs if a platform that the package supports takes it".
- Rulings for batch 6, "Library behaviour on supported platforms (path;
  the referee, adopted by the lead)" (`benchmark-rules.md:2463`): "a call
  back into the package that happens on any supported platform and
  admitted Python version is an edge, by the library call-back rule (B5).
  A trace recorded on one platform does not limit this union ... `path`
  declares `OS Independent` and tests on Windows, so the 38 call-backs
  that `ntpath` and `pathlib` make into `Path.replace` and `Path.__radd__`
  stay."
- "Implementation, version and platform combinations (path; the referee,
  adopted by the lead)" (`benchmark-rules.md:2593`): "Only combinations
  on which the implementation exists are considered, with that runtime's
  real library behaviour. So `path` admits PyPy 3.11 on Windows ... 5
  call-backs".
- Clarifications (2026-11-15), "Versions and configuration": "Include
  names across the release's admitted Python 3 versions"; Edges: "on any
  Python version that the release supports".
- B2: a client `str` with an embedded null is a value of the `Path`
  constructor's public argument.

The rules decide it: both path rulings were made on this package, name
these mechanisms, and adopt the union over platforms, versions and
implementations.

**4. The evidence.**

- CPython 3.12.16 `Lib/ntpath.py:204-216` (read in `python:3.12-slim`):
  `normp = p.replace(altsep, sep)`; for `\\server\share` without a third
  separator, `return p, empty, empty` returns the object itself.
- CPython 3.10.22 `Lib/ntpath.py:180` (`splitdrive`): `normp =
  p.replace(altsep, sep)`.
- CPython 3.12 `Lib/ntpath.py:481`: `from nt import _path_normpath as
  normpath` with a Python fallback on `ImportError`; PyPy 3.11's `nt`
  exports none (`path.md` Codex round 2, from the PyPy 3.11 v7.3.20
  source in the audit records' `deps/`).
- path's `Path` overrides `replace` (string replace or file rename by
  arity), `__add__`, `__radd__`; `str` methods on a subclass dispatch to
  them, so the call-backs are package code.

**5. Against.** These edges test whether a tool models the private
implementation of `ntpath` on Windows and of PyPy's `nt` module, not the
package; a static analysis that reads one host's stdlib or typeshed
cannot see them, and they move with patch-level stdlib changes. The
benchmark chose the union over runtimes on purpose (Edges: "on any Python
version that the release supports"; "A trace recorded on one platform
does not limit this union"); narrowing it to the analysing host's runtime
would change the definition of an edge for every package. The inside
edges here are real calls of package methods on supported runtimes.
