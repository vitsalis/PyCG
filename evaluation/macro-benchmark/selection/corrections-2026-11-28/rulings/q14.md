# Q14. The name of asyncio's default event loop

Adopted by the lead in place of a referee, maintainer's instruction of
2026-11-28. Read at `c7fc8fb3`. Paths are relative to
`evaluation/macro-benchmark/`; a package's files are cited from its root
under `projects/<name>/`, its ground truth is under `ground-truth/`, the
micro cases are under `evaluation/micro-benchmark/snippets/`, and `deps/`
is the dependency sources of batch 8.

**1. The question.** The micro ground truth names the methods of the
default loop `asyncio.EventLoop.*`; the macro ground truths name them
`asyncio.SelectorEventLoop.*` and `asyncio.ProactorEventLoop.*`. A
`common/same_function.json` group cannot join the two, because
`asyncio.EventLoop` exists only from Python 3.13 and a group needs "one
object on every supported CPython (3.12 to 3.15)". Which name is the
convention?

| Benchmark | Site | Caller | Callees at `c7fc8fb3` |
|---|---|---|---|
| micro | `async/call_soon_callback`, `loop.call_soon(tick)` on `get_running_loop()` | `main.start` | `asyncio.EventLoop.call_soon` |
| micro | `async/explicit_event_loop`, `loop.run_until_complete(...)`, `loop.close()` on `new_event_loop()` | `main` | `asyncio.EventLoop.run_until_complete`, `asyncio.EventLoop.close` |
| aiocache | `backends/memory.py:38:50`, `73:54` `loop.call_later(...)` on `get_running_loop()` | `SimpleMemoryBackend._set`, `._expire` | `asyncio.SelectorEventLoop.call_later`, `asyncio.ProactorEventLoop.call_later` (`aiocache.ledger:285-289`, `320-324`) |
| bottle | `bottle.py:3793:69` `self.loop.stop()` on `asyncio.new_event_loop()` | `AiohttpServer.run.<lambda1>` | `asyncio.SelectorEventLoop.stop`, `asyncio.ProactorEventLoop.stop`, `uvloop.new_event_loop.stop` (`bottle.ledger:4655-4659`) |

No other macro package calls a method of an asyncio loop (pyrate-limiter
and django-constance only call `asyncio.get_running_loop()`).

**2. The ruling.** **A public name that a module binds to another public
name of the same class (`EventLoop = SelectorEventLoop`) is a second
alias, not a further class path: the receiver keeps the name it is bound
from. The default loop is `asyncio.SelectorEventLoop` on Unix and
`asyncio.ProactorEventLoop` on Windows on every admitted version;
`asyncio.EventLoop` adds no name.**

Scope: this decides between two public aliases of one class on one
runtime. It does not change the order public alias, exported type
attribute, type name of `ruling-names-2.md` and the batch-8 C-type ruling
(`threading.Lock` still replaces `_thread.LockType` from 3.13, since
`_thread` is not a public path), and it does not touch a name that the
package itself writes (an explicit `asyncio.TimeoutError(...)` or a base
class named in a `class` statement keeps its written path). A factory is
not an alias.

Effect:

| Where | Change |
|---|---|
| aiocache, bottle, structlog | none (16 edges stay as they are) |
| `async/call_soon_callback/callgraph.json` | `main.start -> asyncio.EventLoop.call_soon` renamed `asyncio.SelectorEventLoop.call_soon` (edge and node) |
| `async/explicit_event_loop/callgraph.json` | `main -> asyncio.EventLoop.run_until_complete` and `main -> asyncio.EventLoop.close` renamed `asyncio.SelectorEventLoop.run_until_complete` and `.close` (edges and nodes) |
| `benchmark-rules.md`, micro Names, Methods | one sentence: a public name that a module binds to another public name of the class adds no path |
| `common/same_function.json` | no group needed |

The validator accepts the new micro names: they resolve to the same
functions on the validator's interpreter (CPython 3.14 and 3.15, Linux).

**3. What the rules say.**

- Micro Names, Methods: "The public import path of the class of the
  instance". "The ground truth uses the path as the snippet reaches it";
  here the snippet reaches the loop through a function, not a path.
- "Callees outside the package": "A method of an outside object is named
  by the class of the receiver, also when that class inherits it"; "One
  class reached through two import paths is one callee when the class is
  known."
- Clarifications 2026-11-15, "Outside names": "A direct alias of a class
  is a class path"; "Versions and configuration": "Retain an older
  fallback name where that runtime lacks the later public path. Do not
  add two aliases for one class on the same runtime."
- `ruling-names-2.md` (Corrections of 2026-11-25): "A direct public class
  alias names the receiver's class in each admitted implementation,
  version and configuration where that attribute actually holds the class
  ... One name per class in each configuration; the names are the union
  over the admitted configurations". Its precedents choose between a
  public alias and a private name (`threading.Lock` over
  `_thread.LockType` from 3.13; `hashlib.blake2b` over `_blake2.blake2b`).

The rules do not decide this. On CPython 3.13 and later the loop's class
has two public aliases in the same module, and "one name per class" does
not say which. On 3.12 and earlier only `SelectorEventLoop` and
`ProactorEventLoop` exist, so the macro names are right there; the open
question was the name on 3.13 and later, and with it the micro name.

**4. The evidence.** `deps/cpython/<v>/Lib/asyncio/`:

| Version | Unix (`unix_events.py`) | Windows (`windows_events.py`) |
|---|---|---|
| 3.12.16 | `class _UnixSelectorEventLoop` (`:57`); `SelectorEventLoop = _UnixSelectorEventLoop` (`:1499`); no `EventLoop` | `class ProactorEventLoop` (`:310`); `SelectorEventLoop = _WindowsSelectorEventLoop` (`:890`); `DefaultEventLoopPolicy = WindowsProactorEventLoopPolicy` (`:901`); no `EventLoop` |
| 3.13.18 | `SelectorEventLoop = _UnixSelectorEventLoop` (`:1548`); `EventLoop = SelectorEventLoop` (`:1550`); `'EventLoop'` in `__all__` (`:35`) | `EventLoop = ProactorEventLoop` (`:906`); in `__all__` (`:33`) |
| 3.14.10 | `:1029`; `EventLoop = SelectorEventLoop` (`:1031`) | `EventLoop = ProactorEventLoop` (`:906`) |
| 3.15.2 | `:1029`; `:1031` | `:899` |

`asyncio/__init__.py` star-imports the platform module and extends
`__all__` with it (3.13.18 `:43-47`). The default loop is the policy's
`_loop_factory`, `_UnixSelectorEventLoop` on Unix (3.14.10
`unix_events.py:1026`) and `ProactorEventLoop` on Windows
(`windows_events.py:902`); `asyncio.run` makes it through
`events.new_event_loop()` (3.14.10 `runners.py:146-147`).

So `asyncio.EventLoop` is bound from the other public name: it is
`SelectorEventLoop` on Unix and `ProactorEventLoop` on Windows, one name
for two classes depending on the platform, and it exists from 3.13 only.
`SelectorEventLoop` and `ProactorEventLoop` hold their classes on every
admitted version.

The traces (CPython 3.14.10, Linux) name the callee where it is defined,
`asyncio.base_events.BaseEventLoop.call_later` and `.run_in_executor`,
with both `asyncio.SelectorEventLoop.*` and `asyncio.EventLoop.*` among
the aliases (`dynamic/aiocache.json`, `dynamic/structlog.json`).
aiocache's ledger already states the rule at its sites: "asyncio.EventLoop
is an alias of these same classes, not a third callee"
(`aiocache.ledger:289`, `324`).

aiocache (3.7 and later), bottle (2.7 and 3.8 and later) and structlog
(3.10 and later) all admit versions before and after 3.13, and Windows.

**5. Against.** On 3.13 and later `asyncio.EventLoop` is the name that
asyncio added for the platform's default loop, and the 2026-11-15 clause
"Retain an older fallback name where that runtime lacks the later public
path" reads as preferring the later public path. That reading would keep
the micro names and add `asyncio.EventLoop.*` beside the old names in the
macro ground truths (+8 outside edges: aiocache 2, bottle 1, structlog 5),
giving two names for one class across the admitted versions where one
name holds on all of them, and a name whose class changes with the
platform. The clause was written for private fallback names
(`_sre.SRE_Pattern` against `re.Pattern`), where the later name is the
only public one; it does not choose between two public names. A second,
weaker argument: on Windows, the micro name
`asyncio.SelectorEventLoop.close` would not resolve to the running loop's
`close`, while `asyncio.EventLoop.close` would; the validator runs on
Linux only.
