# Q3. fabric: paramiko and invoke as missing libraries

Adopted by the lead in place of a referee, maintainer's instruction of
2026-11-28. Read at `c7fc8fb3`. Paths are relative to
`evaluation/macro-benchmark/`; a package's files are cited from its root
under `projects/<name>/`, its ground truth is under `ground-truth/`, and
`benchmark-rules.md:<n>` is a line of `evaluation/benchmark-rules.md` at
that commit.

**1. The question.** fabric's ground truth names paramiko and invoke
callees by their access paths as missing modules, although typeshed has
paramiko stubs and "the environment installs it". About 30 false
positives of the study pair with false negatives of the same call, for
example:

| Caller (`fabric.` omitted) | Site | Ground truth | The study's name |
|---|---|---|---|
| `connection.Connection.open` | `connection.py:524` | `paramiko.client.SSHClient.connect` | `paramiko.SSHClient.connect` |
| `connection.Connection.create_session` | `588` | `paramiko.client.SSHClient.get_transport.open_session` | `paramiko.Transport.open_session` |
| `runners.Remote.read_proc_stdout` | `runners.py:35` | `paramiko.client.SSHClient.get_transport.open_session.recv` | `invoke.Runner.channel.recv` |
| `transfer.Transfer.put` | `transfer.py:268` | `paramiko.client.SSHClient.open_sftp.put` | `paramiko.SFTPClient.put` |
| `tunnels.Tunnel.read_and_write` | `tunnels.py:154` | `paramiko.transport.Transport.open_channel.recv` | `paramiko.Channel.recv` |

fabric imports `from paramiko.client import SSHClient, AutoAddPolicy`,
`from paramiko.config import SSHConfig` (`connection.py:17-20`), and
invoke's `Context`, `Config`, `Runner`, `ExceptionHandlingThread`.

**2. The ruling.** **Apply the missing-module rule; no edge changes. A
library is installed for the ground truth only when the project's test
environment installs it; a tool's bundled stubs, typeshed included, are
not a source for names.** fabric's paramiko and invoke callees keep their
access paths.

The `dependencies` key of `projects.toml` installs nothing, and the row
of the "`projects.toml`" table of `benchmark-rules.md` that read
"Installed top-level modules that are library code" says what the key
means: the top-level modules of the libraries that the package imports,
directly or through other libraries, which `trace.py` counts as library
code where they are installed, while `test_requirements` is what the test
environment installs.

Effect: 0 edges in fabric or elsewhere; the wording of the
`dependencies` row.

**3. What the rules say.**

- Ground-truth conventions, "Callees outside the package"
  (`benchmark-rules.md:1877-1881`): "A call into a third-party module
  that is not installed is named as a missing module by the
  micro-benchmark rules (markdown2: `wavedrom.render`), also when a copy
  of the library can be read (dagster-pipes, bottle, pyrate-limiter)."
- Micro-benchmark "Missing modules" (`benchmark-rules.md:4223`) and
  "Names" (`:4168`): "Missing modules: The access path (`ext.Cls.fun`)";
  calling a stub returns an instance of that stub, whose attribute has
  the longer path.
- Clarifications (2026-11-15), "Missing libraries"
  (`benchmark-rules.md:2280`): "Reading a library does not make ordinary
  calls transparent ... direct attribute/call chains retain their
  imported access path."
- "Writing a ground truth" step 2: "Never use the output of PyCG or of
  any other static analysis tool." Nothing in the rules makes typeshed
  (or any tool's bundled stubs) part of a ground truth;
  `benchmark-rules.md` does not mention typeshed.
- `fabric.md` J1 applies these rules; the corrections of 2026-11-25
  (`../corrections-2026-11-25/rulings/ruling-fabric-1.md`) extended the
  access paths through constructors.

The rules decide it: the access-path names are right.

**4. The evidence.**

- fabric has no test run and no test environment: its `projects.toml`
  table has no `test_requirements`; there is no
  `test-environments/fabric*.txt`; invoke 1.x (required `>=1.0,<2.0`)
  imports `imp` and cannot import on CPython 3.12 and later (its
  `projects.toml` notes). No trace exists. So no benchmark environment
  installs paramiko or invoke.
- The evaluation images do not install them either: `pip list` in
  `pycg-eval-macro`, `pycg-ci-macro` and `pycg-eval-runner` (run with
  `--network none`) lists neither, and no `paramiko` directory exists in
  them.
- What has paramiko is PyCG: `crates/stubs/stub_data/third_party/
  paramiko.json` (typeshed `types-paramiko` 5.1,
  `crates/stubs/stub_data/README.md:141`). That is tool knowledge, which
  the ground truth must not use.
- `benchmark-rules.md:102` documented `dependencies` as "Installed
  top-level modules that are library code", and fabric's entry lists
  `invoke`, `paramiko`, `six`, `decorator`, `win32api`. `trace.py:126`
  reads the key only to decide whether installed code under
  `site-packages` is library or client code; for a project without a test
  run nothing is installed. This wording is the likely source of "the
  environment installs it".

**5. Against.** The access paths are not paths that resolve to the
function that runs (`paramiko.client.SSHClient.get_transport.open_session.recv`
is `paramiko.channel.Channel.recv` at run time), while the
micro-benchmark's general name rule asks for "a dotted path that resolves
to the function that runs"; a tool that uses paramiko's real types is
scored as a false positive and a false negative for each call. The
missing-module convention exists so that a ground truth needs no library
behaviour beyond the package; class names here would need a decision on
which library sources may name results, for every package with missing
libraries (dagster-pipes, bottle, pyrate-limiter, einops, pgvector,
django-constance, ...), which is a convention change, not a fabric
correction.
