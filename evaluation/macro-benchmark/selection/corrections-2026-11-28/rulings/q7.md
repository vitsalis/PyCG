# Q7. Fallback hash classes and `_sre.SRE_Pattern`: are they reachable?

Adopted by the lead in place of a referee, maintainer's instruction of
2026-11-28. Read at `c7fc8fb3`. Paths are relative to
`evaluation/macro-benchmark/`; a package's files are cited from its root
under `projects/<name>/`, its ground truth is under `ground-truth/`,
`benchmark-rules.md:<n>` is a line of `evaluation/benchmark-rules.md` at
that commit, and `deps/` is the dependency sources of batch 8.

**1. The question.** Two families of outside names exist only on some
runtimes. Do the version and implementation rules admit the runtimes that
make these receivers?

- **Builtin hash classes**, which `hashlib` returns only when OpenSSL does
  not give the hash: `_sha1.SHA1Type`, `_sha256.SHA256Type`/`SHA224Type`
  (CPython 3.8 to 3.11), `_sha2.SHA*Type` (3.12 and later),
  `_sha512.SHA512Type`, `_sha512.SHA384Type`, `_md5.MD5Type`, `_sha3.*`,
  and the PyPy names `_md5.md5`, `_sha1.sha`, `_sha256.sha256`,
  `_sha512.sha512`, ... 63 graph edges in 10 packages:

- **`_sre.SRE_Pattern` and `_sre.SRE_Match`**, the compiled-pattern and
  match types before CPython 3.7: 58 graph edges in 6 packages (pypinyin
  39, Sublist3r 11, funcy 3, configargparse 2, segno 2, autojump 1). Every
  one of these sites also has the `re.Pattern.*` or `re.Match.*` name.

**2. The ruling.** **Apply the existing rules: hashlib's builtin fallback
is a documented library configuration on every admitted CPython and PyPy
("Versions and configuration", 2026-11-15), so its receiver classes are
named by the batch-8 C-type ruling and `ruling-names-2.md`;
`_sre.SRE_Pattern` and `_sre.SRE_Match` are named wherever the release
admits a CPython 3 before 3.7 (segno ruling).** A trace recorded with
OpenSSL on CPython 3.14 does not limit this union.

This does not admit a configuration that a client makes by changing
package internals, and it does not add a fallback name where the release
admits no runtime that lacks the later public path.

Effect: no edge added, removed or renamed; no text of
`benchmark-rules.md` changes.

Open item: the CPython 3.0 to 3.6 sources that Sublist3r's note cites
(3.0.1, 3.1.5, 3.2.6, 3.3.7, 3.4.10 `sha1module.c`) and that the `_sre`
names rest on are not among the dependency sources of batch 8; a reader
cannot re-check those names without fetching them.

**3. What the rules say.**

- Clarifications 2026-11-15, "Versions and configuration": "Documented
  interpreter or library configuration counts when it changes a
  package-owned default or value (`-u` changes the binary standard
  streams; hashlib's documented fallback changes the concrete SHA-1
  receiver)." And: "Include names across the release's admitted Python 3
  versions. ... Retain an older fallback name where that runtime lacks the
  later public path. Do not add two aliases for one class on the same
  runtime."
- Batch 8, "A C type exported under a module attribute other than its
  type name" (`../batch-8-proposal/rulings/b8-ruling-c-type-names-1.md`):
  names `_sha256.SHA256Type` on 3.8 to 3.11, `_md5.MD5Type`,
  `_sha1.SHA1Type`, the 3.10-3.11 `_sha512.SHA384Type` overwrite, and the
  PyPy type names.
- Corrections of 2026-11-25, `ruling-names-2.md`: PyPy's builtin MD5 and
  SHA-2 classes are `hashlib.md5`, `hashlib.sha256`, ... where hashlib
  falls back to them; at `hashlib.new(name)` the private names stay beside
  the aliases ("no source excludes the fallback").
- Batch 7, "Compiled patterns on CPython 3.6 (segno)": "When CPython 3.6
  is admitted, compiled-pattern methods retain `_sre.SRE_Pattern.<method>`
  beside their `re.Pattern.<method>` names on 3.7 and later, as
  configargparse, funcy and pypinyin have them. Removing an old test
  environment without withdrawing support does not exclude that version."
- Judgements: "The supported versions are those that the package
  declares: where it declares Python 2, a branch that only Python 2 takes
  runs, and its builtin callees have the Python 3 name of the type".

The rules decide both parts: the hash fallback is admitted by name in the
2026-11-15 clarification and named by two later rulings; the pre-3.7
pattern types are admitted by the segno ruling wherever the release
admits such a version.

**4. The evidence.**

Hash fallback (`deps/cpython`, `deps/pypy`):

- CPython 3.10.22 `Lib/hashlib.py`: `import _hashlib` in a `try`
  (`:169`); on `ImportError` the module sets `_hashlib = None` and takes
  the builtin constructors for `new` and the named functions
  (`:175-178`). With `_hashlib` present, a named constructor whose OpenSSL
  probe raises `AttributeError` or `ValueError` falls back too
  (`:140-141`), and `hashlib.new` catches the `ValueError` of
  `_hashlib.new` and builds the builtin object (`:161-166`). The docstring
  guarantees md5, sha1, sha224, sha256, sha384 and sha512 "to exist" on
  every platform (`:17-18`). 3.12.16 (`:140-141`, `:175-176`) and 3.15.2
  (`:158-159`, `:195-196`) keep both fallbacks.
- `_hashlib` is the OpenSSL extension: `Modules/Setup` of 3.10.22 builds
  it from `_hashopenssl.c` with `-lcrypto` (`:215-217`), and documents the
  builtin modules for a system without OpenSSL (`:251-252`, "normally only
  built if the system does not have the OpenSSL libs"). A CPython built
  without OpenSSL is a documented build configuration.
- PyPy 3.10 v7.3.19 `lib-python/3/hashlib.py` has the same structure
  (`import _hashlib` at `:170-171`, `except ImportError` at `:176-179`,
  probe fallback at `:141`).
- The ground truths cite these sources at each site; for example
  websocket-client `_handshake.py:215:53` names `_sha1.SHA1Type.digest`
  from `Modules/sha1module.c` of 3.10.22 to 3.15.2, and Sublist3r
  `sublist3r.py:554:127` keeps the type name `_sha1.sha1` for CPython 3.0
  to 3.3, which export no `SHA1Type`.

Pre-3.7 pattern types:

|---|---|---|
| autojump | Python 2.6+ and 3.3+ (README; tox py26, py27, py33-py35) | yes |
| configargparse | `python_requires=">=3.6"` (`configargparse.md:13`) | yes |
| funcy | Python 3.4 and later, CPython and PyPy (`funcy.md:346`) | yes |

| Sublist3r | `python_requires='>=2.7'` (`Sublist3r.md:95-96`) | yes |

A sweep of all ledgers: each of the 6 packages pairs every `_sre.SRE_X.m`
with `re.X.m` at the same site and the reverse; no other package that
names `re.Pattern` or `re.Match` admits a CPython 3 before 3.7 (the others
declare 3.7 or later, or, as bottle, Python 2.7 and 3.8+, whose Python 2
library names follow Python 3 by the Judgements rule). The `_sre` type
names rest on the segno ruling and the configargparse judgement
(`configargparse.md:252-254`).

**5. Against.** No admitted release of these packages documents running
on a CPython without OpenSSL, and every mainstream CPython build links
OpenSSL, so the fallback is a build that hardly anyone runs; ten packages
carry 63 edges for it. The 2026-11-15 clarification answers it: a
documented library configuration counts, "The configuration need not be
repeated in each package's documentation", and the probe fallback
(`hashlib.py:140-141`) also fires on an OpenSSL build that lacks or
blocks an algorithm, which no source excludes. Against the `_sre` part:
CPython 3.6 is long out of support; but the rules follow the release's
declaration, not the CPython support calendar (segno: "Removing an old
test environment without withdrawing support does not exclude that
version").
