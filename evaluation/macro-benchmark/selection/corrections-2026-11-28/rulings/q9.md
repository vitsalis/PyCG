# Q9. more-itertools and funcy: do the iterable and lazy-object roles follow B2?

Adopted by the lead in place of a referee, maintainer's instruction of
2026-11-28. Read at `c7fc8fb3`. Paths are relative to
`evaluation/macro-benchmark/`; a package's files are cited from its root
under `projects/<name>/`, its ground truth is under `ground-truth/`, and
`benchmark-rules.md:<n>` is a line of `evaluation/benchmark-rules.md` at
that commit.

**1. The question.** Three readings of B2:

| Part | Package | Reading | Ground-truth extent | Study count |
|---|---|---|---|---|
| (a) | more-itertools 11.2.1 | `_concurrent_tee.__iter__`/`__next__` are callees at ordinary iterable-role sites | 289 sites, 265 inside pairs to `_concurrent_tee.*` | 264 FN |
| (b) | more-itertools | `Iterable[_NumberT]` (and the other numeric and index inputs) admit only `numeric_range`, not the package iterators | e.g. `running_mean`, `running_min`, `running_max`, `running_median`, `running_statistics` and their helpers (`recipes.py:1346-1589`); `split_into` `more.py:1774`; `sort_together` `2008`, `2012`; `sample` `4039`, `4043`; `extract` `5442`, `5447` | about 230 FP |
| (c) | funcy | a documented lazy object (the iterator that `map`, `filter`, `keep`, `remove`, `where`, `takewhile` return) carries all admitted package callbacks of its factory into the consumers that the documentation hands it to | 9 consumer sites whose notes cite this admission (`seqs.py:29:16`, `32:16`, `63:16`, `141:16`, `178:16`, `331:23`; `colls.py:131:26`, `225:16`; `funcs.py:137:31`), 139 inside pairs at them; J5 itself added 48 | 205 FN |

**2. The ruling.** **Apply the batch-6 iterable rulings and the
factory-output clarification; no change.** (a) A `_concurrent_tee` from
the public factory fits every ordinary source-iterable input; (b) numeric
and index inputs admit compatible `numeric_range` objects only; (c) a lazy
object that the documentation hands to a consumer carries the admitted
callbacks of its factory's public arguments, at that consumer only.

Scope: (c) does not admit a factory output at a consumer that no
document, test or package call gives it to, nor a client-built library
wrapper around a package object (B5).

Effect: 0 edges in more-itertools and funcy.

`docs/seqs.rst:331` ("essentially a shortcut for `cat(map(f, *seqs))`")
hands `map`'s output to `cat`, which is `chain.from_iterable`
(`seqs.py:179`), a library function, not to `lcat`; it is no witness for
the `lcat` site (found by the audit of these corrections). That site
rests on `README.rst:70` and on the package's own call in `lmapcat`
(`seqs.py:197`, `return lcat(map(f, *seqs))`, with `lmapcat`'s public
`f`), and the notes at `funcy.ledger:2315-2323` say so. No edge changes.

**3. What the rules say.**

(a) Rulings for batch 6, "Declared iterable types (B2; more-itertools;
the referee, adopted by the lead)" (`benchmark-rules.md:2303`): "The
private `_concurrent_tee` instances that the public `concurrent_tee`
returns also fit this role: its documentation names those outputs as
inputs to `serialize` (`more.py:5535`), and the factory-output
clarification applies; a `_concurrent_tee` built in another way is not
considered." "This role" is the "one ordinary source-iterable role" that
the same ruling finds in the documentation (`README.rst:8`;
`docs/api.rst:270`; `more.py:5499`). "Inner ordinary iterables keep the
eleven members" (eight stub-declared iterators, `numeric_range`,
`SequenceView`, `_concurrent_tee`).

(b) The same ruling, "the referee's second ruling, after the blind
audit": "specialising the item type of an outside `Iterable` annotation
does not by itself admit every member of the ordinary source-iterable
role. For the numeric and index inputs (`sizes`, `key_list`, weights,
counts, indices, an iterable shape and the data of the `running_*`
functions), compatible `numeric_range` instances are admitted ...
`SequenceView` and the nine iterator members are not admitted there
merely because they can carry numbers."

(c) B2 (`benchmark-rules.md:2052-2065`): a package value is in scope
"when the documentation names it for that role ... or when the package's
own code, tests or documented examples pass it there"; "An expression in
the documentation that passes a package function in a role is a
documented example, in prose as in a code block". Clarifications
(2026-11-15), "Factory outputs (B2)" (`benchmark-rules.md:2228`): "When
documentation names a package factory's output for an input role, the
output is admitted with the factory's public arguments. An example does
not restrict those arguments to its one value. The output must be
constructible through that public API; this does not admit hidden
closures or arbitrary package callables." B4's per-entry reading of
funcy's documentation (`benchmark-rules.md:2160-2165`).

The rules decide all three: (a) and (b) are the text of the batch-6
ruling; (c) is the factory-output clarification applied per consumer.

**4. The evidence.**

(a) `more.py:5528-5548`: `concurrent_tee` returns a tuple of
`_concurrent_tee(iterable)` and `_concurrent_tee(iterator)` objects; the
docstring (`:5535-5537`) says to wrap one with `serialize`, whose
parameter is an ordinary `Iterable[_T]`. `_concurrent_tee.__iter__`
returns `self`, `__next__` advances (`:5563-5575`). Each site keeps only
the operations Python makes (`more-itertools.md`, "What a member runs").

(b) `recipes.pyi:78`: `_NumberT = TypeVar("_NumberT", float, Decimal,
Fraction)`; `running_mean`, `running_min`, `running_max`,
`running_statistics` take `iterable: Iterable[_NumberT]`
(`recipes.pyi:209-232`). No document, test or package call passes a
package iterator there; `numeric_range` is documented as a producer of
numeric ranges (`more.py:2266-2299`).

(c) Each consumer site cites its own documentation of the factory output
at that consumer:

| Consumer site | Documentation |
|---|---|
| `lcat`, `seqs.py:178:16` | `README.rst:70` `lcat(map(range, range(4)))`; the package's `lmapcat`, `seqs.py:197` `return lcat(map(f, *seqs))` |
| `_lfilter`, `seqs.py:32:16` | `docs/seqs.rst:301` `lkeep(f, seq) == lfilter(bool, map(f, seq))` |
| `first`, `seqs.py:63:16` | `docs/seqs.rst:312-314` `first(keep(...))` |
| `some`, `colls.py:225:16` | `docs/seqs.rst:316` "the same with `some` and `map`" |
| `lremove`, `seqs.py:141:16` | `docs/primitives.rst:12` `remove(isnone, map(silent(int), ...))` |
| `group_values`, `seqs.py:331:23` | `docs/seqs.rst:434` `group_values(keep(r'...', sys.argv))` |
| `walk`, `colls.py:131:26` | `docs/colls.rst:48` `walk(compose(str, ord), 'ABC')` |
| `ilen`, `seqs.py:113:10` | `docs/seqs.rst:179` `ilen(takewhile(...))` |

The factory's public mapper argument then takes every value admitted for
that factory's own role (J1: the per-entry roles of `map`/`lmap`), not
only the example's `range` or `silent(int)`, which is what the
clarification says. It is not "every consumer": a consumer without such
documentation (for example the `seq` of `distinct`, `seqs.py:236-248`, or
of `with_prev`, `421-422`) gets no lazy-object callbacks.

**5. Against.** For (a): the only documented consumer of a
`concurrent_tee` output is `serialize`; spreading it to about 130
consumers rests on the referee's "one role" reading of the composition
prose, a reading the second ruling narrowed for numeric inputs but not
for this class. For (c): the documented examples pass one specific mapper
each; combining "the consumer admits this factory's output" with "the
factory admits all its role values" multiplies two admissions that no
single example shows together. The 2026-11-15 clarification adopted
exactly that combination ("An example does not restrict those arguments
to its one value"), so undoing it is a change of a global clarification,
not an audit correction.
