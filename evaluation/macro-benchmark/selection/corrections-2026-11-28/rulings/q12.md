# Q12. django-constance: judgement 2's self-edges and judgement 3's cache

Adopted by the lead in place of a referee, maintainer's instruction of
2026-11-28. Read at `c7fc8fb3`; django-constance 4.5.0 (`1032c50`). Paths
are relative to `evaluation/macro-benchmark/`; a package's files are
cited from its root under `projects/<name>/`, its ground truth is under
`ground-truth/`, and `benchmark-rules.md:<n>` is a line of
`evaluation/benchmark-rules.md` at that commit.

**1. The question.** (a) Judgement 2 (`django-constance.md:132-176`)
makes `AsyncValueProxy` dunder methods call themselves: the graph has 29
self-edges `AsyncValueProxy.__X__ -> AsyncValueProxy.__X__` and 65
proxy-to-proxy pairs in all (the study: about 40 false negatives, 35 of
them with a proxy caller). Are they right?

(b) Judgement 3 treats the object that
`caches[settings.DATABASE_CACHE_BACKEND]` returns
(`backends/database.py:34`) as client code, so the 11 calls on
`self._cache` (`database.py:53`, `58`, `77`, `80`, `86`, `95`, `98`,
`104`, `115`, `159`, `174`) have no callee (the study: 13 false
positives, for example `DatabaseBackend.get ->
django.core.cache.caches.get`). Should they be named?

**2. The ruling.** **Apply django-constance rulings (e), (a) and (b); no
change.**

Scope: (a) covers only the recursion through a proxy that an admitted
backend stores unchanged. (b) does not admit a successor of a documented
class that the admitted library releases lack; if the package's
documentation named `PyMemcacheCache`, its methods would be callees.

Effect: 0 edges; no text of `benchmark-rules.md` changes.

**3. What the rules say.**

(a) Rulings for batch 6, django-constance (e), "Package-produced stored
proxies" (`benchmark-rules.md:2514`): "A value that package code reads
and later restores through its public helper stays admitted when an
admitted backend stores it unchanged: under a running event loop,
`override_config` can restore an `AsyncValueProxy` into the memory
backend, and the calls that then recurse through the proxy count before
the `RecursionError` (3 and 36 edges stay). A later call whose preceding
step must raise is not reached."

(b) The same ruling, (a) "Configured implementations (B2, B5)"
(`benchmark-rules.md:2483`): "When package or library code resolves a
class, callable or module that a supported setting names, the
configuration-selection rule applies whichever code resolves the name:
the defaults of the package and of the library, and the admitted
documented configurations, count ... A configured implementation that
the client defines stays client code." (b) "Test configurations"
(`benchmark-rules.md:2490`): the package's tests count for a
configuration "that selects a concrete library implementation by name
... It admits no implementation that a test defines, no mock". B5's
configuration clause (`benchmark-rules.md:2204-2210`, whitenoise): "any
other configured class is client code". B3: an object left behind after
the package raised to refuse it is not considered.

The rules decide both parts: (e) was made for exactly the recursion of
(a); (a) and (b) of the same ruling decide the cache.

**4. The evidence.**

(a) `base.py` `AsyncValueProxy`: each dunder reads
`self._get_sync_value()` and applies the operation to the result; with a
proxy stored in `MemoryBackend` (restored by `override_config.disable`,
`test/pytest.py:43`, `49`; `test/unittest.py:90`, `103`), the result is a
proxy and the same dunder runs on it until `RecursionError`. The Redis
and Database backends raise `TypeError` in `dumps` first.

(b) Who can be the cache:

| Candidate | Source | Admitted? |
|---|---|---|
| Django's default `CACHES` (`LocMemCache`, `conf/global_settings.py:522` in Django 6.1.2) | library default | refused: `isinstance(self._cache, LocMemCache)` raises `ImproperlyConfigured` (`database.py:34-39`); B3 then excludes the half-built backend |
| `django.core.cache.backends.memcached.MemcachedCache` | the package's documented configuration (`docs/backends.rst:124-130`) | absent from every admitted Django (4.2 to 6.1): Django removed it in 4.1 (`django-constance.md` J9 verified its absence in 6.1.2) |
| `tests.cache_mockup.Cache` | the package's test settings (`tests/settings.py:32-37`) | a `BaseCache` subclass that the tests define (`tests/cache_mockup.py:5-20`): excluded by ruling (b) |
| any other Django backend (`PyMemcacheCache`, `RedisCache`, `DatabaseCache`, `FileBasedCache`, `DummyCache`) | client configuration, undocumented by the package | client code by ruling (a) and the whitenoise clause |

So no admitted configuration yields a cache whose methods can run, and
the 11 sites keep no callee. The study's names
(`django.core.cache.caches.get`) are also not a name the conventions
give: Django is installed, so no access path applies, and a subscript
result has no inferred path ("Missing libraries", 2026-11-15).

**5. Against (b).** The documentation's intent is "a cross-process Django
cache backend"; its one example names a class that Django renamed, and
every real deployment uses a Django built-in backend whose `get`/`set`
run library code that a reader can name (`BaseCache` subclasses).
Treating every such configuration as client code leaves the cache branch
of `DatabaseBackend` with no outside callees at all. The rules choose
documented configurations over intent (whitenoise, django-constance
(a)); admitting "the documented class's successor" would be a new
ruling, with the edge effect of up to 11 sites times the admitted backend
classes.
