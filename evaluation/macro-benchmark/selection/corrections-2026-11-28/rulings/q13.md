# Q13. toolz `check_valid`: the PyPy path and the 97 excluded lambdas

Adopted by the lead in place of a referee, maintainer's instruction of
2026-11-28. Read at `c7fc8fb3`; toolz 1.2.0 (`451af60`). Paths are
relative to `evaluation/macro-benchmark/`; a package's files are cited
from its root under `projects/<name>/`, its ground truth is under
`ground-truth/`, and `benchmark-rules.md:<n>` is a line of
`evaluation/benchmark-rules.md` at that commit.

**1. The question.** `check_valid` (`toolz/_signatures.py:674-687`) calls
`func(*args, **kwargs)` at `684:13`, where `func` is a lambda of the
signature registry that `_is_valid_args` (`:690-695`) looks up by the
client's callable. The ground truth has 193 registry lambdas as callees
there and two `exclude` lines with 97 more (51 + 46). Is this consistent?
A PyPy-only path (`functoolz.py:939-947`, where every registry key goes
to the registry functions) puts every registry lambda in scope, while 97
are excluded "on run-time identity of operator functions".

**2. The ruling.** **Apply the toolz ruling; no change.** A
dispatch-table target is a callee only if the table holds it on an
admitted runtime; names missing on every admitted runtime and entries
replaced by an identical key are not targets. The PyPy path widens which
keys reach `_is_valid_args` (all of them, not only those without a
signature); it cannot reach a lambda that is in no stored entry.

Effect: 0 edges; no text of `benchmark-rules.md` changes.

**3. What the rules say.** Rulings for batch 8, "A dispatch table of the
package selected by a client input (toolz J4; the referee,
`b8-ruling-toolz-1.md`)" (`benchmark-rules.md:3064`): "An admitted public
input may select a handler that the package installs in its own dispatch
table ... and each target needs a witness on an admitted runtime that
reaches the call and binds, accounting for overwritten entries and
short-circuiting ... toolz's `check_valid` keeps all 193 registry
lambdas, the six package keys included ...; no edge changed, and the
exclusions are 51 unavailable names and 46 overwritten entries."

The toolz ruling decides it. "Every registry lambda in scope" means every
lambda that the registry holds on some admitted runtime; a lambda that no
runtime stores under any key cannot be selected by any callable, on PyPy
or CPython. The two exclusion groups are not a judgement on the identity
of values that a client passes; they are facts of the registry's
construction.

**4. The evidence.** `create_signature_registry`
(`_signatures.py:664-671`) stores `signatures[getattr(module, name)] =
new_sigs` for each name that the module has. So a lambda is reachable
only if (i) its name exists on the runtime and (ii) no later entry with
an identical key object replaces its entry.

The registry construction was run in containers (the toolz source
mounted read-only, `--network none`, `python -I`), and each lambda was
mapped to the ledger's `<lambdaN>` numbering by an `ast` pass over
`_signatures.py`:

| Runtime | Reachable | Name missing | Overwritten |
|---|---:|---:|---:|
| CPython 3.10.22 | 191 | 53 | 46 |
| CPython 3.12.16 | 191 | 53 | 46 |
| CPython 3.13.18 | 191 | 53 | 46 |
| CPython 3.14.10 | 191 | 53 | 46 |

- The 191 reachable lambdas are all ledger callees; no overwritten lambda
  is a callee. The two callees that these runtimes lack are `<lambda42>`
  and `<lambda43>`, the entries of `builtins.frozendict`
  (`_signatures.py:112-114`), a builtin from CPython 3.15 (admitted). So
  51 names are missing on every admitted runtime, as the ruling says, and
  193 = 191 + 2.
- The 46 overwritten: `operator.py` defines `__add__ = add` and the other
  dunder aliases after `from _operator import *` (CPython 3.14
  `Lib/operator.py:422`, `438`; the same order in 3.10, 3.12 and
  3.13, read in the official images), so `operator.__x__ is operator.x`
  and the later `operator.x` entry replaces the `operator.__x__` entry:
  45 lambdas. `operator._abs is builtins.abs` (checked on 3.10 to 3.13), so
  `operator._abs`'s entry replaces `builtins.abs`'s: 1 lambda.
- PyPy 3.9 to 3.11 use the same `lib-python/3/operator.py` order (the
  audit's derivation, `toolz.audit.md:264`, read the PyPy sources in the
  audit records).

**5. Against.** The 45 aliases are excluded because of an implementation
detail (`__x__` and `x` are one function object); were they distinct on
some runtime, 45 more lambdas would be callees. That holds for every
CPython `Lib/operator.py` and, by the audit's reading, for PyPy's copy; a
PyPy build with a native `operator` that defined the dunders separately
would change it, and none of the admitted PyPy releases is such a build
as far as the audit records show.
