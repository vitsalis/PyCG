# Q6. `array.array` against `array.ArrayType`

Adopted by the lead in place of a referee, maintainer's instruction of
2026-11-28. Read at `c7fc8fb3`. Paths are relative to
`evaluation/macro-benchmark/`; a package's files are cited from its root
under `projects/<name>/`, its ground truth is under `ground-truth/`,
`benchmark-rules.md:<n>` is a line of `evaluation/benchmark-rules.md` at
that commit, and `deps/` is the dependency sources of batch 8.

**1. The question.** The study scored a tool's `array.ArrayType.*` names
as true positives in pgvector and jsonpickle (16) but as false positives
in pyusb, where the ground truth has `array.array.*` (15 false negatives,
15 false positives). Which name is the convention?

Every ledger uses `array.array` and none uses `array.ArrayType`:

| Package | Sites | Callees |
|---|---|---|
| pyusb | `usb/_interop.py:61:27`, `64:27`, `69:27`; `usb/util.py:160:23` | `array.array` |
| pyusb | 14 `buffer_info()` sites in `usb/backend/libusb0.py` (599:43, 669:39, 679:43, 690:43, 703:40), `libusb1.py` (660:43, 894:40, 931:43, 947:43), `openusb.py` (654:51, 664:51, 674:51, 684:51, 717:51) | `array.array.buffer_info` |
| pyusb | `usb/util.py:321:31` | `array.array.tobytes` |
| pgvector | `pgvector/vector.py` and `halfvec.py`, 17 sites | `array.array`, `.frombytes`, `.byteswap`, `.tolist` |
| jsonpickle | `handlers.py:149:57`, `157:27` | `array.array.tolist`, `array.array` |
| asciinema, websocket-client, textdistance | 5 sites | `array.array` |

The sources reach the class only as `array.array` (`import array` and
`array.array(...)` in pyusb, `from array import array` in pgvector,
`array.array` in jsonpickle `handlers.py:157`, `160`); none writes
`ArrayType`. Over all ledgers and graphs the names are `array.array` and
its `buffer_info`, `byteswap`, `frombytes`, `tobytes` and `tolist`, and
no other.

**2. The ruling.** **`array.array` is the name of the class, as the
packages import it; `array.ArrayType` is a second alias of the same class
on every runtime and adds no name (one class, one name).** The ground
truths already follow it.

The asymmetry of the question is in the scoring: the scorer turns a
trace's aliases into identities per package, so the score depended on
which alias a package's trace happened to record. It must not.
`evaluation/common/same_function.json` holds groups `array.array` /
`array.ArrayType` and `array.array.<m>` / `array.ArrayType.<m>` for the
members that the ground truths name (`buffer_info`, `byteswap`,
`frombytes`, `tobytes`, `tolist`): its condition, "one object on every
supported CPython (3.12 to 3.15)", holds (section 4).

Effect: no edge added, removed or renamed in any package; six groups in
`same_function.json`.

**3. What the rules say.**

- Micro conventions, Names: "The ground truth uses the path as the
  snippet reaches it: Functions of a module: The path that the snippet
  imports"; "Methods: The public import path of the class of the
  instance".
- "Callees outside the package": "One class reached through two import
  paths is one callee when the class is known."
- Clarifications 2026-11-15, "Versions and configuration": "Do not add two
  aliases for one class on the same runtime." Corrections of 2026-11-25,
  `ruling-names-2.md`: "One name per class in each configuration".

The rules decide it: one class, one name, and the name is the path the
package uses, `array.array`.

**4. The evidence.**

- CPython exports one type object under both attributes. In
  `deps/cpython/<v>/Modules/arraymodule.c` the module adds the type as
  `ArrayType` and, through `PyModule_AddType`, under the last component of
  its type name `array.array` (`.name`); 3.7.17 adds the same object under
  both names with `PyModule_AddObject`:

  | Version | `.name = "array.array"` | `ArrayType` | `array` |
  |---|---|---|---|
  | 3.7.17 | | `:3039` | `:3041` |
  | 3.10.22 | `:2856` | `:3058` | `:3083` |
  | 3.12.16 | `:2849` | `:3081` | `:3102` |
  | 3.13.18 | `:3053` | `:3286` ("Older undocumented alias", `:3285`) | `:3304` |
  | 3.14.10 | `:3086` | `:3320` (`:3319`) | `:3338` |
  | 3.15.2 | `:3294` | `:3527` (`:3526`) | `:3545` |

  CPython has no `Lib/array.py`; the module is this extension. The
  methods are entries of the one type's `array_methods` table, so
  `array.ArrayType.<m>` and `array.array.<m>` are one method descriptor.
- `evaluation/common/lookup.py` resolves all twelve names of the six
  groups to one object per group on CPython 3.12.16, 3.13.18, 3.14.10 and
  3.15.2 (the official images, `--network none`).
- PyPy binds both attributes to one class:
  `pypy/module/array/moduledef.py` of pypy3.10-v7.3.19, `'array'` and
  `'ArrayType'` both `interp_array.W_ArrayBase` (lines 5-6), whose TypeDef
  is named `'array.array'` (`interp_array.py:788-789`).
- The traces name the class `array.array` and record `array.ArrayType`
  as an alias (`dynamic/<name>.json`, `aliases`): pgvector for
  `array.array`, `.byteswap`, `.frombytes` and `.tolist`; jsonpickle for
  `array.array` and `.tolist`; pyusb only for `array.array`: its trace
  (16 tests) has no edge to `buffer_info` or `tobytes`.
- The scorer turns a trace alias into an identity per package
  (`evaluation/common/score.py:184-193`, `identities`): a tool name equal
  to an alias that the package's own trace recorded counts as the
  canonical name. So `array.ArrayType.tolist` matched in pgvector and
  jsonpickle, and `array.ArrayType.buffer_info` could not match in pyusb.

**5. Against.** A scorer that rewards `array.ArrayType.tolist` in
pgvector treats the alias as correct, so leaving pyusb's 15 pairs
unmatched was a double standard; the groups remove it without changing a
ground truth. The name in the ground truth stays `array.array`: CPython
itself calls `ArrayType` an "Older undocumented alias" (3.15.2
`arraymodule.c:3526`), and a trace alias is not a naming rule (Format of
`dynamic/<name>.json`: the canonical name is where the callee is
defined).
